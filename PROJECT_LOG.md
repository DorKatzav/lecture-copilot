- **Incident — memory.** First fixture replay: pressure "warning", swap +11.2 GB; second: +7.7 GB, the Ollama runner (`llama-server`) at 10.1–18 GB for an 8.3 GB model. Root cause (reproduced, `eval/m1.json` `prompt_cache`): Ollama 0.34.2 runs models in llama-server, which keeps the KV state of every distinct prompt in host RAM up to 8 GiB (`--cache-ram`, default 8192). Chunk prompts never repeat, so the cache only grows: 4.5 → 13.6 GB over 6 prompts of one chunk's size; with the cache off the runner stays at 4.5 GB and prompt evaluation takes the same 1.9 s.
- **D-M1-4** (ruling): Ollama is started by `scripts/ollama_serve.sh` with `LLAMA_ARG_CACHE_RAM=0`; gate check `prompt_cache` reads the running server's environment (seen failing on a plain `ollama serve`). Alternatives: a smaller cache (still unused memory — chunk prompts share only the system prompt); a Modelfile parameter (none exists for this). Cost: no prefix reuse between calls — measured as zero difference. Input for M5: the launcher must start Ollama through this script.
- **D-M1-3** (ruling, corrected): every request that can load a model sends the same `OLLAMA_LOAD_OPTIONS` (`num_ctx`, `use_mmap`), so Ollama never reloads mid-lecture. The first runner was seen with `--load-mode none` and 9.3 GB of anonymous memory for the weights; with `use_mmap` it was 1.5 GB. **Not reproduced:** on a fresh load the default and `use_mmap` runners were identical (`eval/m1.json` `runner`), so when Ollama picks `none` is unknown. The commit message of e13c05f credits `use_mmap` with the whole fix; the measured cause of the growth is the prompt cache (D-M1-4). `use_mmap` stays as an explicit setting.
